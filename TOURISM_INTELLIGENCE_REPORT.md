# NYC Tourism Intelligence implementation

This extends the existing project, not a replacement system. Twelve street-experience definitions, OSM routing, dark visual language and the existing GPS/maneuver engine are preserved. Source data is never replaced by generated businesses, reviews, room inventory or prices.

## Measured audit and coverage

See DATA_AUDIT_REPORT.md and data/audit.json (generated by scripts, not estimated): 20,654 Manhattan discovery category records, 20,654 distinct source record IDs, no repeated source record IDs, 20,437 canonical IDs, 217 intentional linked records sharing canonical IDs and 13 retained conflict flags. These numbers do not prove historical merges are all semantically correct. Stronger matching protects future refreshes; the raw legacy source objects must be refetched to reconstruct previously merged entities.

New sources: NYC Parks Properties `enfh-gkve` (2,061 property records across all five published boroughs) and NYC Public Restrooms `i7jb-7jku` (1,066 source rows, 1,063 retained; three rejected for incomplete identity/coordinates). No borough is invented for the restroom records. Source park-property inventory also includes non-visitor land; undeveloped/operations/lot/parkway/strip/building/managed-site/cemetery subtypes are excluded from ordinary park discovery, not passed off as visitor parks. Source timestamps and retrieval times are listed in the audit. New points are discovery-only unless an exact same-publisher facility identity matches the existing verified network snapshot. This linked 226 existing restroom records by exact name/operator/coordinate identity and preserves 19 publisher-reported unavailable statuses; it does not claim they are live observations.

The registry has 114 dataset rows and 922,369 thematic/source records. These totals include multiple views of the same geometry, not 922,369 unique tourism entities. Existing DOHMH permits already cover five boroughs. Museums, named hotels and general attraction discovery remain mostly Manhattan. Routing/scoring remains Manhattan only.

## Data and update behaviour

- New citywide snapshots first check publisher versions; unchanged sources are not downloaded again. Updates validate identity/coordinates and large count regressions before atomic file replacement.
- POI refreshes serialize/validate before publishing, retain previous files outside the checkout, replace the index last and restore files on a write error. This is file-based rollback, not a fully isolated database transaction. Failed required enrichments abort instead of silently discarding known data.
- DOHMH gzip replacement is staged and preserves a prior version. Full API refreshes are used where a reliable delta cursor is unavailable; no false incremental cursor is invented.
- A daily/manual GitHub Actions audit produces a validated artifact for review; it does not automatically overwrite production. Long-term snapshots still need reviewed publication.
- Do not run a full OSM/Wikidata rebuild while the required Wikidata enrichment is blocked. Existing valid source snapshots are retained.

## Agent requirements and APIs

`journey.requirements` preserves review evidence requirements, numeric 5-point rating limits when explicitly requested, USD restaurant/ticket/total/nightly limits, dates, party and beds. `journey.counts` represents explicit total visits (e.g. two landmarks); `more` remains an incremental follow-up. Monetary fields never become measured street scores. Unsupported monetary guarantees fail explicitly. The local preview retains specific coffee/pizza/tiramisu intent and obvious review/hotel/count requirements; it remains limited parsing, not a replacement for genuine AI.

Reused endpoints: place search/details/ratings, official menu verify, food recommendation, itinerary, detours, route scoring, GPS progress. Added `GET /api/places/categories`, `GET /api/hotels/search` (static listings, bed/price criteria unverified). Place profiles add source/update/verification scope, field provenance/conflicts and alias IDs. Menu responses add a typed requested-item profile with `complete:false`, evidence status, freshness and price association. No complete restaurant inventory is implied. Menu images may use optional OCR but OCR matches remain probable, not verified prices/items.

Required menu candidates are accepted into itineraries only while matching backend evidence is fresh. A 12-dimensional route score cannot stand in for dish availability, ratings, hotel inventory or admission eligibility. Required unavailable venues and unsatisfied time limits block Start Navigation until the plan is revised.

## Production and secure setup

No commercial provider newly connected. See PROVIDER_ACCESS.md for actual prerequisites, terms/attribution/cache checks and official links. Never put keys in frontend code or chat. An API key alone is not proof that every field or a MapLibre display is permitted.

Environment network additions were saved as a draft for source discovery/policy checks; draft saving is not publication. Code/data production status must be checked from `/api/status` deployment_commit after merge. No current price, complete menu, licensed reviews or live hotel inventory is claimed without real sources. See the PR and final receipt for production acceptance results.
