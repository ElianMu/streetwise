Generated by `benchmarks/agent_vs_deterministic.py`, run for real on this machine on 2026-10-25. Re-run it
yourself — it writes `benchmarks/baseline.json` fresh each time; nothing below is estimated.

## Deterministic pipeline (`routing/recommend.py`'s `recommend_food`, real local data, 5 requests)

| Metric | Value |
|---|---|
| P50 latency | 3723 ms |
| P95 latency | 6846 ms |
| Mean latency | 3309 ms |
| Peak RSS at measurement | 504.5 MB |

This is slower than it should feel for a "find me food" request, and the likely cause is visible in the code,
not guessed: `recommend_food` runs real-time official-website menu verification (`routing/menu.py`'s `verify`,
with live HTTP fetches up to a `DEADLINE_S=10` budget per candidate) inline, synchronously, for every
candidate that needs it. This was already true before this change — the agent work didn't introduce or fix
it, but benchmarking it for Phase 0 surfaced it honestly. Flagging as a real, separate, pre-existing
performance finding: **worth a dedicated investigation**, out of scope for this task.

## Admission/concurrency sweep (real `Admission` gate from `routing/capacity.py`, `active_limit=2, queue_limit=3`)

| Concurrency attempted | Accepted immediately | Rejected |
|---|---|---|
| 1 | 1 | 0 |
| 5 | 2 | 3 |
| 10 | 2 | 8 |
| 20 | 2 | 18 |

This is the real, already-existing backpressure mechanism that `/api/agent/food-stop` was wired into (as a
"heavy" endpoint, same gate as `/api/routes`/`/api/itinerary`/`/api/recommend/food`) — confirming an agent run
(which makes several internal tool calls, so is more expensive per request) cannot starve the rest of the
server; it's throttled by the same gate at the same `active_limit=2`.

## What this Phase 0 does not cover

- Real agent-path cost-per-request in USD (needs a real key).
- Load testing specifically against the agent endpoint at sustained concurrency (the sweep above tests the
  shared `Admission` gate in isolation, not the agent's own LLM-call latency under load).
- Cold vs. warm start timing for the LangGraph graph compilation itself (observed to be sub-100ms in this
  session's manual testing, not formally benchmarked).
